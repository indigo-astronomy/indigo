# WeMacro Rail generated migration

Status: complete, 2026-09-13. Baseline version: 0x02000005; migrated version: 0x03000006. Hardware tests were explicitly out of scope. The user-facing README remains unchanged.

## Sources and protocol confidence

- Repository guidance: root and `indigo_test/AGENTS.md`, driver-development basics, generator migration guide, serial-simulator contract, common driver-testing scope and focuser standard.
- Production sources: the hand-written driver, public header, standalone wrapper and USB match rules; the host PTY simulator; the current integration test; property, simulator, test, Makefile, Xcode, Windows and migration records.
- Driver-specific repository documentation is limited to the user-facing README and identifies the USB controller, CH341 serial bridge and the separate macOS Bluetooth variant. It contains no wire-protocol specification and must remain byte-identical.
- No manufacturer wire-protocol document is bundled with this driver or published in the manufacturer pages found during research. The manufacturer's [software-setting page](https://www.wemacro.com/?p=331) confirms distance/start-to-end modes, step length, shutter delay/count/interval and return/beep behavior; its [specification page](https://www.wemacro.com/?p=337) confirms 100 mm travel and controller/rail/shutter hardware. Neither documents binary bytes, CRC or status values. The existing implementation is therefore the primary source for the 12-byte binary command format and three-byte status frames; these details are implementation-derived compatibility, not independently documented protocol facts.
- The observed command frame is `A5 5A CMD A B C D3 D2 D1 D0 CRC_LO CRC_HI`; CRC is Modbus/IBM CRC16 with initial value 0xFFFF and polynomial 0xA001 over the first ten bytes. The driver uses commands 0x04 (shutter), 0x20 (stop), 0x40/0x41 (relative directions), 0x80 with option/speed bits (configuration/step size), and 0x10 with option bits (batch execution). Status frames are `A5 5A STATE`; observed states are 0xF0 initial, 0xF5/0xF6 directional completion and 0xF7 batch progress.
- Simulator-backed validation can prove framing, CRC, command translation, queue/property transitions, lifecycle and recovery. It cannot certify undocumented firmware timing/state semantics, physical direction, travel, shutter electrical timing, CH341 behavior, Bluetooth parity, Linux/Windows runtime or actual hardware concurrency.

## Existing behavior and findings

- The driver exposes one relative-only `WeMacro Rail` focuser. Absolute position, limits, temperature, compensation, backlash and GOTO/SYNC are unsupported/hidden. Visible driver-owned controls are two-speed selection, direction, local reverse, relative steps, abort, batch return/beep configuration, fire shutter and five batch parameters.
- The implementation is hand-written API 2 style. Connection work uses a zero-delay timer, commands use a pthread mutex, completion is consumed by an unowned `indigo_async()` reader thread, and teardown relies on closing the descriptor to end that thread. It uses POSIX `select()` and `close()` in the driver, preventing portable Windows compilation.
- `wemacro_read()` conflates timeout, malformed/short frame, EOF and state 0; accepts any first two bytes; can return the third byte of a corrupt frame; and uses one blocking read without exact-length accumulation. No status checksum exists in the observed three-byte format, so strict header and complete-frame validation are essential.
- `wemacro_write()` constructs the documented-by-code CRC but does not validate command-specific fields, and callers frequently ignore its result. Successful property states can therefore be published after transport failure. The command mutex only protects writes; the long-lived reader and connection teardown race on the raw handle.
- Connection is not transactional beyond serial open. CONNECTION becomes OK before controller initialization is validated because the reader starts asynchronously. An invalid/missing initial state later calls `indigo_device_disconnect()` from the reader; clients can observe a false successful connection and initialization failures are not cleanly rolled back.
- The reset fallback sends move/stop/move commands and accepts only 0xF5, but ignores all three write results. Its firmware rationale is undocumented. The initial configuration write is also unchecked.
- Relative motion publishes BUSY before checking whether the command write succeeded. Completion accepts either 0xF5 or 0xF6 regardless of the requested direction. There is no bounded finalizer deadline, explicit stall/transport-failure state or deterministic fresh-operation recovery.
- Abort always publishes OK even when STOP fails. It marks both relative motion and batch ALERT even if neither is active, mutates batch count to zero, and has no serialization/cancellation contract with a pending start or completion callback.
- Speed change sends configuration but always publishes OK. Configuration flags are only cached and do not immediately reach hardware; they affect later speed/batch commands. Shutter always publishes OK even on write failure.
- Batch execution sends a setup command, blocks the handler for 100 ms and sends `COUNT - 1` as an unsigned 32-bit value. COUNT permits zero, so zero underflows to 0xFFFFFFFF. Both write results are ignored. Progress destructively decrements the public requested COUNT value, losing the accepted target. Completion with BACK depends on a later 0xF6; without BACK it depends on the decremented count reaching zero. Unexpected statuses and missing statuses can leave BUSY forever.
- The batch configuration uses `INDIGO_ANY_OF_MANY_RULE`, so BACK and BEEP can be independently enabled as intended. SPEED maps value 2 to byte 0xFF and value 1 to 0. Direction and reverse select 0x40 versus 0x41. The batch setup command deliberately omits BACK/BEEP bits, while the execute command includes them.
- The simulator emits initial status before a command, does not validate length/header/CRC/reserved fields or command-specific ranges, and advances motion/batch only when the driver performs another read. It has no monotonic motion model, journal, fault injection, malformed/split/status-loss behavior, transport lifecycle evidence or alternate startup profiles.
- The current integration suite has one broad compliance case. It checks property/item presence and sends representative controls, but mostly waits for any OK state without fresh revisions, does not verify binary bytes/CRC/order, does not prove BUSY/progress/completion, and omits initialization rollback, failures, no-op/bounds, overlap, abort races, disconnect/reconnect, shutdown refusal, additional instances and resource cleanup.
- The host simulator and test sources are already in Xcode and the test Makefile. `REFACTOR.md` and the future `.driver` are absent. There is no Visual Studio project or solution/server registration. Migration status remains API 2 / no Windows / no generator / no queues / not retested, while the repository README describes the USB driver as platform independent.

## Required acceptance coverage

The final inventory maps every applicable relative-focuser and custom rail requirement to named scenarios with fresh property revisions and bounded waits. It covers protocol framing/CRC/byte order/command grammar; property metadata and visibility; transactional initialization/rollback; two speeds, directions and reversal; relative motion BUSY/completion; boundaries/no-op/overlap; stop/failure/disconnect/recovery; BACK/BEEP/shutter; complete batch parameters, progress and both return modes; lifecycle/additional instances/resource balance; malformed/split/suppressed operation outcomes; command failure and recovery. Silent status loss exercises the same bounded timeout path as a physically stalled operation; the simulator also supports an explicit stall fault for diagnosis. Relative position progress is non-applicable because the device exposes no position readback.

Generic framework numeric validation, persistence internals and hidden unsupported absolute/temperature/compensation controls are not driver tests. Physical direction/travel, shutter electrical behavior, real timing, CH341/Bluetooth behavior, hardware concurrency and Linux/Windows execution remain hardware/platform validation and are not claimed.
