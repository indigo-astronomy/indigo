3. Concepts & Terminology

a. Camera ID (camId) vs Camera SN (Serial Number)

Please distinguish between camera ID (camId) and camera SN:
(a) SN is unique and persistent, fixed inside the camera and remains unchanged, and does not change with connection or system restart.
(b) Camera ID (camId) may change due to connection or system restart. Enumerate the cameras to get the camera ID, and then call the Open function to pass in the camId parameter to open the camera.

b. Modes for accessing image data: "ImagePtr" mode vs "Frame memory copy" Mode

1. ImagePtr mode

The application obtains a pointer to the frame buffer directly from the SDK, eliminating the need to copy frame data and thus improving performance. It calls Mallincam_PullImagePtr to retrieve the frame buffer and Mallincam_PushImagePtr to return it.

typedef struct {
    unsigned id;                    /* Each frame buffer is assigned a unique ID, 0 is reserved as an invalid id */
    unsigned char pixelFormat;      /* MALLINCAM_PIXELFORMAT_xxxx */
    unsigned char ergb;             /* see MALLINCAM_OPTION_RGB */
    unsigned char snapR;            /* see Mallincam_SnapR */
    unsigned char infoVer;          /* MallincamFrameInfo version, >= 4 */
    unsigned reserved;
    unsigned strideRaw;             /* RAW data stride, 0 means no padding */
    MallincamFrameInfoV4* ptrInfo;
    void* snapCtx;
    void* ptrRaw;                   /* RAW, see MALLINCAM_OPTION_IMAGEPTRRAW */
    unsigned char* ptr8;            /* 8bits, RGB24, RGB32, Grey8 */
    unsigned short* ptr16;          /* 16bits RGB48, RGB64, Grey16 */
} MallincamImagePtr;

2. Frame memory copy (memcpy) mode

Frame data is memcpy from the SDK internal buffer to the user-provided buffer. Compared to the ImagePtr mode, this introduces an extra copy and results in a performance penalty.

"Pull mode" and "Push Mode" are Functionally equivalent. The former is recommended since it's simpler and the application seldom gets stuck in multithreading conditions, especially when using windows message to notify the events.

  • In Pull Mode, mallincam plays a passive role and the application 'PULL' image data from mallincam. The internal thread of mallincam obtains image data from the camera hardware and saves them to the internal buffers, then notify the application (see below). The application then call functions Mallincam_PullImageV4(V3) or Mallincam_PullImage(WithRowPitch)(V2), Mallincam_PullStillImage(WithRowPitch)(V2) to access image data.

There are to ways to notify applications:

a) Use Windows message: Start pull mode by using the function Mallincam_StartPullModeWithWndMsg. When event occurs, mallincam will post message (PostMessage) to the specified window. Parameter WPARAM is the event type, refer to the definition of MALLINCAM_EVENT_xxxx. This model avoids the multithreading issues, so it's the most simple way. (Obviously, this is only supported in Windows systems, and not supported in Linux and macOS.)

b) Use Callback function: Start pull mode by using the function Mallincam_StartPullModeWithCallback. When event occurs, mallincam will callback the function PMALLINCAM_EVENT_CALLBACK.

  • In Push Mode, mallincam plays an active role. Once the video data is obtained from camera by internal thread, mallincam will 'PUSH' the image data to the application through PMALLINCAM_DATA_CALLBACK. Call the function Mallincam_StartPushMode to start push mode. Push mode is more complex. There are some special precautions, such as multithread issues, being impossible to call Mallincam_Close and Mallincam_Stop in callback function PMALLINCAM_DATA_CALLBACK_V4/V3, etc.

d. Still Capture (Still Image)

Most cameras support the so-called still capture capability. This function switches the camera to another resolution temporarily when the camera is in preview mode, after a "still" image in the new resolution is captured and then switch back to the original resolution and resume preview mode.

For example, UCMOS05100KPA support 3 resolutions and the current one in preview mode is 1280 * 960. Call Mallincam_Snap(h, 0) to "still capture" an image in 2592 * 1944 resolution. To realize this function, the camera will temporarily switch to 2592 * 1944 firstly, get an image in 2592 * 1944 resolution and then switch back to 1280 * 960 and resume preview.

a) In pull mode operation, after the still capture, MALLINCAM_EVENT_STILLIMAGE will be sent out for external acknowledgement. The external application should call Mallincam_PullImageV4(V3) or Mallincam_PullStillImage(V2) to get the still captured image.
b) In push mode operation, after the still capture, the callback function PMALLINCAM_DATA_CALLBACK_V4/V3 will be called with bSnap parameter setting TRUE. The image information including the resolution information will be obtained via the parameter pHeader.

To check whether the camera have the still capture capability, call Mallincam_get_StillResolutionNumber function or check the still field of the struct MallincamModelV2.

e. Data format: RGB vs RAW

Mallincam supports two data formats: RGB format (default) and RAW format. RAW format could be enabled by assigning MALLINCAM_OPTION_RAW parameter to 1 when calling Mallincam_put_Option function.

  • RGB format: The output of every pixel contains 3 componants which stand for R/G/B value respectively. This output is a processed output from the internal color processing engine.
  • RAW format: In this format, the output is the raw data directly output from the sensor. The RAW format is for the users that want to skip the internal color processing and obtain the raw data for user-specific purpose (RAW = -1 slightly different, indicating partial processing). With the raw format output enabled, the functions that are related to the internal color processing will not work, such as Mallincam_put_Hue or Mallincam_AwbOnce function and so on.

Users could switch these two format by calling Mallincam_put_Option function with different value setting to MALLINCAM_OPTION_RAW. You change this option only when camera is NOT running.

Users could change RGB bits by calling Mallincam_put_Option with different value setting to MALLINCAM_OPTION_RGB. You change this option only when camera is NOT running.

f. White Balance and Auto White Balance: Temp/Tint mode vs RGB Gain mode

1. Mallincam sdk supports two independent modes for white balance: a) Temp/Tint Mode; b) RGB Gain Mode

a) Temp/Tint mode is the default white balance mode. In this mode, temp and tint are the parameters that could be used to control the white balance. Mallincam_get_TempTint function is used to acquire the temp and tint values and Mallincam_put_TempTint is used to set the temp and tint values. Function Mallincam_AwbOnce is used to execute the auto white balance. When the white balance parameters change, MALLINCAM_EVENT_TEMPTINT event will be notified for external use.

b) In RGB Gain mode, the while balace is controled by the gain values of the R,G,B channels. Mallincam_get_WhiteBalanceGain is used to acquire the parameters and Mallincam_put_WhiteBalanceGain is used to set the white balance parameters. Mallincam_AwbInit is used to execute the execute the auto white balance. When the white balance parameters change, MALLINCAM_EVENT_WBGAIN event will be notified for external use.

The functions for these two modes cannot be misused:

a) In Temp/Tint mode, please use Mallincam_get_TempTint and Mallincam_put_TempTint and Mallincam_AwbOnce. Mallincam_get_WhiteBalanceGain and Mallincam_put_WhiteBalanceGain and Mallincam_AwbInit cannot be used, they always return E_NOTIMPL.
b) In RGB Gain mode, please use Mallincam_get_WhiteBalanceGain and Mallincam_put_WhiteBalanceGain and Mallincam_AwbInit. Mallincam_get_TempTint and Mallincam_put_TempTint and Mallincam_AwbOnce cannot be used, they always return E_NOTIMPL

This mode is specified when the camera is opened and cannot be changed unless the camera is closed and opened again. Please see here.

2. There are two auto white balance mechanisms available in this field: one is continuous auto white balance and the other is a "once" auto white balance. The white balance parameters will be always calculated and updated for the continuous auto white balance mechanism. For "once" auto white balance mechanism, the white balance parameters will be calculated and updated only when triggered. Mallincam cameras support "once" auto white balance mechanism since it is more accurate and propriate for the microscope application, especially when the background is in pure color. Continuous white balance mechanism will encounter some problem in some cases.

3. Monochromatic camera does not support white balance. The functions metioned above always return E_NOTIMPL.

g. Trigger Mode

1. What is Trigger Mode

Mallincam camera has two working modes: video mode and trigger mode. When in trigger mode, no images will be available until the trigger conditions are met. Cameras have 2 types for triggering according to the types of trigger source, including software trigger mode, external trigger mode and simulated trigger mode.

2. The Difference between Trigger and Snap

Trigger mode is designed for accurate control of the camera and images would be acquired only when the conditions are met. Users could get the images by controlling the trigger conditions. Trigger mode must be pre-specified. Once the trigger mode is entered, no images will come out from the camera until the trigger conditions are met. The triggered images will stay the same property as the pre-specified resolution. Snap is designed to acquire the images from the camera in video mode. The resolution of the snapped image could be the same resolution as the video or could be different.

3. Software Trigger Mode

Camera could be triggered by software. In software trigger mode, images burst out only when users trigger the camera from the software. Numbers of the images of the triggering could also be controlled by software.

4. External Trigger Mode

Camera could be triggered by external trigger signal. By now Mallincam camera only supports positive-edge trigger mode.

5. Mix Trigger Mode

Both external and software trigger are enabled.

6. Simulated Trigger Mode

For cameras that do not support software trigger and external trigger, simulated trigger mode could be available. When in simulated trigger mode, the camera hardware actually works in the same mode as the video mode. But the up-level software will not obtain any images from the camera. The software buffer will stay empty until the user set the trigger conditions by software.

7. How to Enter the Trigger Mode

After the numeration of the connected camera, you can check the flag and find out what trigger mode does the camera support according to the following definition. 
#define MALLINCAM_FLAG_TRIGGER_SOFTWARE   0x00080000  /* support software trigger */
#define MALLINCAM_FLAG_TRIGGER_EXTERNAL   0x00100000  /* support external trigger */
#define MALLINCAM_FLAG_TRIGGER_SINGLE     0x00200000  /* only support trigger single: one trigger, one image */
Function Mallincam_put_Option(HMallincam h, unsigned iOption, int iValue) could be used to set the camera to trigger mode when assign MALLINCAM_OPTION_TRIGGER to the iOption parameter. iValue is used to specify the types of the trigger modes. Please see the following for reference. 
#define MALLINCAM_OPTION_TRIGGER   0x0b    /* 0 = video mode, 1 = software or simulated trigger mode, 2 = external trigger mode, 3 = external + software trigger, default value = 0 */
Function Mallincam_get_Option(HMallincam h, unsigned iOption, int* piValue) could be used to get what type of trigger mode the camera is in.

8. How to Trigger the camera

Function Mallincam_Trigger(HMallincam h, unsigned short nNumber) could be used to trigger the camera. Assigning different value to nNumber means different:
nNumber = 0 means stop the trigger.
nNumber = 0xFFFF means trigger continuously, the same as video mode;
nNumber = other valid values means nNumber images will come out from the camera.
If the MALLINCAM_FLAG_TRIGGER_SINGLE flag is checked, the nNumber parameter must be assigned to 1 and 1 image will come out from the camera when Mallincam_Trigger is called.
Enter the trigger mode first and then call Mallincam_Trigger function to trigger the camera.

9. Trigger timeout

The timeout is recommended for not less than (Exposure Time * 102% + 4 Seconds).

h. Thread safe

We use a "thread-safety neutral" policy (similar to C++ standard library), which means:

a) A camera object is thread-safe for reading from multiple threads. For example, given a camera object A, it is safe to read A from thread 1 and from thread 2 simultaneously.

b) If a camera object is being written to by one thread, then all reads and writes to that object on the same or other threads must be protected. For example, given a camera object A, if thread 1 is writing to A, then thread 2 must be prevented from reading from or writing to A.

c) It's safe to read and write to one camera object even if another thread is reading or writing to a different camera object. For example, given camera objects A and B, it's safe when A is being written in thread 1 and B is being read or write in thread 2.

d) It's safe to pull image from multi threads

i. Log file

The SDK does not output logs by default. If there is a file with the same name and extension *.log in the directory where the SDK library file is located and it has write permission, the log will be enabled and recorded in this file:

a) The log file name is exactly the same as the library file, and the extension is changed to *.log (e.g. mallincam.dll corresponds to the log file mallincam.log; xyz.dll to xyz.log; libxyz.so to libxyz.log)

b) The log file time uses relative time by default, and the SDK startup time is recorded as [00:00:00.000]. If you want to use local time (e.g. [0923 17:11:01.491]), add the letter "l" to *.log (i.e. *.llog)

c) By default, the log file content is automatically cleared every time SDK is started, and the log is written from the beginning. Adding the letter "a" to *.log means that the append mode is used, and the log file content is not cleared when SDK is restarted (i.e. *.alog)

d) By default, logging is written to file synchronously. If logging is suspected to block normal operations, append the letter “s” to the *.log file name to enable asynchronous logging (i.e. *.slog)

e) Please make sure that the program has write permission to the log file(For example, if the program is installed in the Program Files directory, it often happens that the log file cannot be written in non-administrator mode. It is recommended to run the program in administrator mode or modify the permission of the log file.)

  • Callback: PMALLINCAM_EVENT_CALLBACK and PMALLINCAM_DATA_CALLBACK_V4/V3

    These callback functions are called back from the internal thread in mallincam.dll, so great attention should be paid to multithread issue.

    (a) Do NOT call Mallincam_Stop and Mallincam_Close in this callback function, otherwise, deadlocks.
    (b) Do NOT call Mallincam_put_Option with MALLINCAM_OPTION_TRIGGER, MALLINCAM_OPTION_BITDEPTH, MALLINCAM_OPTION_PIXEL_FORMAT, MALLINCAM_OPTION_BINNING, MALLINCAM_OPTION_ROTATE, it will fail with the error code E_WRONG_THREAD.

    Remarks: After a frame buffer has been used, it must be returned to the SDK for reuse. Please note the following:

5. .NET (C# & VB.NET)

Mallincam does support .NET development environment (C# and VB.NET).

mallincam.cs use P/Invoke to call into mallincam.dll. Copy mallincam.cs to your C# project, please reference samples.

Please pay attation to that the object of the C# class Mallincam. Mallincam must be obtained by static mothod Open or OpenByIndex, it cannot be obtained by obj = new Mallincam (The constructor is private on purpose).

Most properties and methods of the Mallincam class P/Invoke into the corresponding Mallincam_xxxx functions of mallincam.dll/so. So, the descriptions of the Mallincam_xxxx function are also applicable for the corresponding C# properties or methods. For example, the C# Snap method call the function Mallincam_Snap, the descriptions of the Mallincam_Snap function is applicable for C# Snap method:

[DllImport("mallincam.dll", ExactSpelling = true, CallingConvention = CallingConvention.StdCall)]
private static extern int Mallincam_Snap(SafeHMallincamHandle h, uint nResolutionIndex);

public bool Snap(uint nResolutionIndex)
{
    if (_handle == null || _handle.IsInvalid || _handle.IsClosed)
        return false;
    return (Mallincam_Snap(_handle, nResolutionIndex) >= 0);
}

VB.NET is similar with C#, not otherwise specified.

8. GigE Camera

a. Enable Jumbo Frames on the network interface card (NIC). Using smaller packet sizes will result in lower performance.

Enable Jumbo Frameson Windows:
(1) start "Device Manager", then expand Network adapters. snapshot
(2) Right click the network interface card and select "Properties"
(3) Select the Advanced tab. Next, select "Jumbo Packet" in the Property box, and then select "9014 Bytes" (Different network card models may have slightly different value) for Value to the right. Click OK to save the change. snapshot
(4) Run the following command to view the network card MTU: snapshot
netsh interface ipv4 show subinterface

b. GigE Performance Driver

This driver is optional: not recommended for 1.0G cameras; recommended for 10G cameras.
If you decide to install, please use the command line (Administrator mode), cd to the directory where the .inf file is located, and execute the following statement to install (install.cmd). If there is an old version, need to uninstall the old version first, and then install the new version: 
Install:   netcfg.exe -v -l gigepdrv.inf -c s -i gigepdrv
Uninstall: netcfg.exe -u gigepdrv

c. Firewall and NIC protocols

(1) Recommend to disable the firewall for the NIC used by the network camera. Run in PowerShell (Administrator mode):
Disable firewall (NIC name "xx"):  Set-NetFirewallProfile -Name Private,Public,Domain -DisabledInterfaceAliases "xx"
Restore all NIC: Set-NetFirewallProfile -Name Private,Public,Domain -DisabledInterfaceAliases @()
(2) Recommend to remove or disable irrelevant NIC protocols and drivers (such as the Npcap Packet Driver, QoS, LLDP, etc). In the most streamlined configuration, only the "Gige Performance Driver" and "TCP/IPv4" should remain enabled.

d. The automatic camera discovery process uses broadcast packets with the address 255.255.255.255. Please ensure that your system's security policies do not block network broadcasts.
