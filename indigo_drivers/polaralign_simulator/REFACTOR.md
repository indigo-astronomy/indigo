## Current-state audit

### Architecture, properties and behavior

This is a hand-written, single-device, in-process software simulator. It has no `.driver` generator input, transport, external simulator process, protocol, vendor SDK, firmware or physical resource. `Makefile.drv` builds static, dynamic and standalone forms. The driver advertises additional instances through the common framework property.

The connected device exposes the eight standard Polar Aligner properties defined by `indigo_polaralign_driver.c`: two-axis `POLARALIGN_OFFSET`, `POLARALIGN_ABORT_MOTION`, two-axis `POLARALIGN_STEPS_PER_DEGREE`, independent altitude/azimuth direction selectors, independent altitude/azimuth zero-position resets and four-axis-limit values. The driver initializes both steps-per-degree values to 360, moves both offsets by 0.5 arcmin per 0.2-second tick, enforces configured limits, supports simultaneous two-axis motion, resets either logical position to zero and aborts active motion at the current simulated position. No custom property exists and no property/item change is planned, so `indigo_docs/PROPERTIES.md` should remain unchanged.

### Synchronization, blocking, errors and lifecycle

Version `0x03000002` dispatches connection through a zero-delay INDIGO timer and motion through a stored recurring `indigo_timer *`. Offset changes synchronously cancel the prior timer on the bus callback, validate limits, and start a replacement motion; abort synchronously cancels the timer. Reset/settings changes also mutate properties directly on the bus callback while a timer callback may be updating offset/private state. There is no mutex, but the timer thread and bus callback can race over current/target positions, limits and property state. `indigo_cancel_timer_sync()` also blocks connection, offset and abort callbacks while a timer callback finishes.

Disconnect synchronously cancels motion and snaps targets to current position; detach invokes the same connection callback. Shutdown is rejected while connected. Private data owns only four position scalars and the timer handle, and is released after device detach.

Limit rejection publishes `ALERT` and keeps measured values unchanged. Already-at-target requests complete immediately. Existing offset overlap cancels/replaces an active move without an explicit BUSY rejection. The queue migration will use the framework BUSY guard for overlap, urgent abort for pending/running operations, and queue serialization for resets/settings. It will preserve limit messages, measured-versus-target semantics, 0.5 arcmin/0.2-second motion and disconnect recovery.

### Build, packaging and supported platforms

At baseline the driver was listed by the root driver build and had Xcode source/header entries, but no Visual Studio project; `MIGRATION_STATUS.md` recorded API 3, Windows No, generator No, async queues No, retested N/A and automated tests Yes. The migration added `REFACTOR.md` and `.driver` to the Xcode group. The later user-requested Windows scope added a dedicated Visual Studio project/filters, solution registration and `indigo_server` dependency. The user changed the requested implementation from a hand-written queue refactor to a code-generator migration after step 1. A partial hand-written queue edit made immediately before that change was fully reverted; the production source was restored before generator migration began.

Generator feasibility audit found that `indigo_tools/indigo_generator.c` already has generic emission paths for `indigo_<device>_attach/change_property/detach`, includes base-driver headers by device type, and explicitly recognizes `POLARALIGN_ABORT_MOTION` as urgent. However, `parse_device_block()` does not accept the `polaralign` device keyword, and its local `char type[8]` buffer cannot hold `polaralign`. Therefore the requested migration cannot be expressed by the unchanged generator.

The available environment is macOS 26.6.2, Darwin 25.6.0, arm64 host. Repository builds produce universal x86_64/arm64 Mach-O artifacts; native arm64 and available x86_64/Rosetta execution were tested. Linux and Windows execution environments are unavailable. The user explicitly waived a native Windows build and accepted static project integration validation; Windows support therefore means the x64/ARM64 Visual Studio build/packaging path is present and structurally validated, not that a Windows binary was executed in this environment.

### Existing tests and gaps

The existing public-bus integration executable contains five cases: metadata, property enumeration, class compliance, move/abort/disconnect/reconnect and limits/reset behavior. It already checks both axes moving to completion, abort stopping updates, fresh movement after reconnect, limit rejection for altitude/azimuth/both, per-axis reset during a move, direction switches, ranges and connected-shutdown rejection.

Coverage gaps relevant to this refactor are: explicit progress on each/simultaneous axes, already-at-target completion, BUSY overlap rejection with original target preserved, abort before the queued start runs, abort while idle, fresh move immediately after abort, both reset orders during active two-axis movement, settings/limits queue completion and accepted-value readback, disconnect before queued start, repeated INIT/SHUTDOWN and race-oriented sanitizer/repeat execution with fresh property observations.

Protocol replies, malformed transport data, open/write/read failures, physical hot-plug, SDK rollback and hardware accuracy are not applicable because the simulator has no such boundary. Generic numeric clamping and common configuration persistence remain framework test responsibilities.

## Hardware-test decision

No hardware testing will be performed. The driver is itself the software simulator and has no supported device model, hardware transport or external controller. Hardware tests run/passed will remain explicitly 0/0, and no simulator result will be represented as physical validation.
