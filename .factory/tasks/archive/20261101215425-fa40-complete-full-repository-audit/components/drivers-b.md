## Confirmed candidates for independent coordinator registration

### B-01 — Falcon publishes ALERT while a healthy move is still running

Functional, medium, high confidence; nonblocking audit follow-up, owner coordinator. `indigo_drivers/rotator_falcon/indigo_rotator_falcon.driver:159–188`: after an accepted MD and settle, line166 sets `ROTATOR_POSITION_PROPERTY->state = INDIGO_ALERT_STATE`; each FD progress read publishes that state before FR reports0. A normal move lasting longer than the settle therefore reports failure throughout actual rotation. The property also loses BUSY admission protection while the worker still owns the move; a later request can replace the public target and queue behind it. Both absolute and relative handlers call this blocking helper; disconnect waits behind its loop, potentially120s. Use handler plus bounded finalizer, retain BUSY while active, cancel/stop on abort/disconnect and finish OK/ALERT only at the outcome. Verify healthy progress state, second request admission, abort and disconnect. This is source control-flow proof; no transport executed.

### B-02 — Trutek accepts frames with an invalid reply checksum

Functional, medium, high confidence; nonblocking audit follow-up, owner coordinator. `indigo_drivers/wheel_trutek/indigo_wheel_trutek.driver:37–44,55–68,116–124` reads four bytes and checks header/opcode/payload but never byte3. Both simulator implementations generate additive checksum byte3; host simulator additionally rejects incorrect request checksums (`wheel_trutek_simulator.c:128–130,164–177`). A corrupted reply `A5 81 03 00` to requested slot3 passes current move checks and publishes slot3/OK although expected checksum is29 hex. Local Python evaluation of exactly those comparisons printed driver_accepts_move_reply=true, driver_reports_OK=true, checksum_valid=false. No frame was sent. Check checksum before all count/position application; add corrupted checksum and healthy reply regressions. Prior payload range/arrival fixes are not undone or claimed broken.

### B-03 — WeMacro Bluetooth encodes an accepted zero batch count as UINT32_MAX

Functional, medium, high confidence; nonblocking audit follow-up, owner coordinator. `indigo_mac_drivers/focuser_wemacro_bt/indigo_focuser_wemacro_bt.m:339` advertises COUNT minimum0; line438 encodes `(uint32_t)count - 1` as the device repetition field. A framework-valid zero becomes `0xffffffff` rather than a zero/no-op, while public count stays0 and subsequent completion decrements can go negative. Portable WeMacro `.driver:476` correctly advertises min1 for its same count-minus-one encoding. Align advertised valid domain with protocol semantics or implement an explicit zero no-op; this is an operational encoding/domain mismatch, not a demand to duplicate framework numeric validation. Verify zero/default/maximum encoded fields with an isolated command sink; hardware repetition behavior is unmeasured. Local arithmetic check confirms zero encodes `0xffffffff`.
