# Development plan

Status: draft, revised 2026-11-06 for D1 = dialect in `mount_lx200`. Steps 1–10 belong to the implementation assignment.

## Approach and affected components
Add a `TOUPTEK` dialect to the generated `indigo_mount_lx200` driver, reusing its shared Meade transaction helpers
(`meade_command`, `meade_no_reply_command`), the ZWO-style `:GU#` status parsing and the meridian encoder where the
SH20 format is identical. SH20-specific commands get their own small helpers: `:MS#` polarity, `:Gm#` digits, `:MP0/1#`,
`:SPc#`, `:GPS#`, `:MH#`/`:MFH#`, `:Sgr`, `:SBz`/`:GBz#` and `:GTS#`. ZWO code paths are not modified. Shared code is factored out
only where the change preserves the ZWO wire trace exactly. Protocol facts come from [protocol.md](protocol.md). No INDI code is copied.

This modifies an existing, migrated driver, so the characterization rules apply. The existing simulator suite and
reference traces for the other 15 dialects are the compatibility contract. They must pass before and after every step.

Affected files:
- `indigo_drivers/mount_lx200/indigo_mount_lx200.driver` and the regenerated `indigo_mount_lx200.c`/`.h` (version 82 → 83).
- `indigo_drivers/mount_lx200/mount_lx200_simulator/mount_lx200_simulator.c`: the `touptek` model and its options.
- `indigo_test/integration/test_mount_lx200_simulator.c`: SH20 cases.
- `indigo_drivers/mount_lx200/PROTOCOL.md`: the ToupTek column, with protocol.md S1–S3 added to its sources.
- `indigo_docs/PROPERTIES.md`: `X_TOUPTEK_*` and the new `X_MOUNT_TYPE` item.
- `MIGRATION_STATUS.md`: the `mount_lx200` `Automated Tests (Sim / HW)` counts only; the Comment column is preserved.
- `indigo_drivers/mount_lx200/README.md`: the supported-devices line only after owner approval, plus the `## Testing` record written
  by `tools/run_driver_test.py`. `TEST_SUMMARY.md` is regenerated by the same script.
- No new files are expected, so no Xcode, solution or Makefile registration is needed. Re-check this at step 9.

## Test strategy
The main evidence is the hardware-free simulator suite, covering the Mount and Guider standards for the new dialect. Not-applicable rows
(custom rate, PEC, alignment, encoders, network) are justified in verification.md. Regression protection for the 15 existing dialects
comes from the existing suite and traces. The hardware run depends on D6.

## Security risks and mitigations
Untrusted serial replies are bounded and validated (N1). No new transport.

## Dependencies and architecture decisions
- No new dependencies and no generator change.
- D1 trade-off: the dialect shares transport, polling and finalizers with 15 dialects, which means less code than a separate driver. The cost is
  a larger regression surface, which the existing suite covers. Without an identification command the SH20 cannot be autodetected.

## Migration, rollout, and rollback
This is an additive dialect, so there is no migration. Rollback is reverting the commit. Users of other dialects see only the new `X_MOUNT_TYPE` item.
